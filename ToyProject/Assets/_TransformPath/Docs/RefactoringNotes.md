# TransformPath 설계 결정 기록

구조 개선에서 내린 주요 결정과 이유입니다. 이전 단계별 기록은 Git의 `2c84686`에 있는 Docs 폴더를 봅니다. 측정값은 모두 이 Mac 하나의 Mono Player, 1,000개 객체 기준입니다.

## 구조

| 결정 | 이유 |
| --- | --- |
| 외부 코드를 작업 밖으로 분리 (`PathExecutionBoundary`) | 복잡성의 근원이 작업 도중 재생을 바꾸는 콜백이었습니다. 알림을 작업 뒤로 미뤄 콜백 뒤 재검사를 65곳에서 22곳으로 줄이고, 도달할 수 없게 된 테스트 56건을 지웠습니다 |
| 리스너 예외는 기록만 함 | 경계 뒤의 콜백은 재생과 무관한 코드입니다. 콜백 실패로 재생이 끝나지 않으니 이를 알릴 별도 경로도 필요 없습니다 |
| Queue는 내부 동기 이벤트를 유지 | 등록과 제약은 상태가 바뀌는 작업 안에서 맞아야 합니다. 경계로 미루면 시작을 거부할 수 없고 리스너가 등록 전 상태를 봅니다 |
| 위치와 Queue 제약을 `PathPlaybackCursor`, `PathQueueConstraintState`로 분리 | `PathFollower`가 1,372줄에서 842줄, 필드가 45개에서 23개로 줄었습니다 |
| Single과 Sequence를 Session 접근자로 통합 | Follower의 분기가 10곳에서 4곳이 되어 이동 코드가 하나로 합쳐졌습니다 |
| Engine, Scope를 Follower로 합침 | 식별자와 정리 작업을 중계만 하는 층이었습니다 |
| Lease, HoldPolicy를 `PathQueueSession`으로 합침 | 등록과 대기 상태의 수명이 같습니다 |
| Pause 상태는 Follower만 소유 | Queue의 별도 플래그가 새 재생에 남아 등록이 있어도 움직이지 않는 결함을 만들었습니다 |
| 호환 코드를 두지 않음 | 세분화 인터페이스, `FormerlySerializedAs`, 공개 Receipt 생성자, 소유자 없는 등록 토큰을 지웠습니다. 공개 표면은 API 기준 파일로 고정합니다 |

## 동작

| 결정 | 이유 |
| --- | --- |
| 지정한 진행 상한만 위반으로 판정 | 재개, 간격 증가, 경로 단축으로 Manager 상한을 넘는 것은 정상 상황인데 재생이 끝났습니다 |
| 재생이 끝난 등록을 앞 Agent로 치지 않음 | 해제 전에 재생이 끝난 Agent 뒤에서 나머지가 영구히 막혔습니다 |
| 위치 0의 이벤트를 실행 | 첫 재생, 매 Loop, 구간 시작에서 작성한 이벤트가 실행되지 않았습니다. 자연 도달과 Seek의 커서 규칙을 나눴습니다 |
| 이벤트 정의를 Rebuild 때 복사 | 매 프레임 SO를 읽지 않고, 재생 중 이벤트 비교가 Revision과 일치합니다 |
| 이동 방식이 바뀌면 값 보간 취소 | 다른 방식의 구간에 보간을 적용하면 예외로 재생이 끝났습니다 |
| 진행 방향을 거리로 계산 | 길이 약 3.16 미만의 경로나 구간에서 회전하지 않았습니다 |
| Seek는 먼저 검증 | 준비되지 않은 Provider에서 상태를 일부 바꾼 뒤 예외를 냈습니다 |
| Single Loop에도 전환 한도 65회 | 한 Tick의 전환 수가 Sequence에만 제한되어 있었습니다 |

## 계산과 성능

| 결정 | 이유 |
| --- | --- |
| 같은 시퀀스의 Follower가 스냅샷 공유 | 경로 변경 때 모든 Follower가 각자 복사했습니다. Update 최대가 48ms에서 7ms 안팎으로, 시작이 22ms에서 2.6ms로 줄고 GC가 사라졌습니다 |
| Queue 프레임을 무할당으로 전환 (삽입 정렬, `PathListeners`) | 프레임당 25~74KB로 2초에 GC가 5회 났습니다. 측정 구간에서 할당과 GC가 0입니다 |
| 등록 조회를 사전으로 변경 | Tick마다 `List.Contains`로 대상 수의 제곱만큼 비용이 들었습니다 |

## 하지 않은 것

- **Loop 이음매 보정:** 이음매 프레임 측정은 직선 경로의 값이라 닫힌 경로의 문제를 보여 주지 못합니다. 근거 없이 보간 규칙을 바꾸지 않았습니다.
- **Loop 경로의 순환 거리 계산:** Queue는 진행도 차이로 간격을 봅니다. Loop Queue가 필요해질 때 순환 거리로 바꿉니다.
- **`PathData.PathChanged`의 경계 편입:** 구독자가 변경 표시만 하고 반영은 다음 Tick에 하므로 작업 중 상태를 바꾸지 않습니다.
- **`PathFollower` 추가 분리:** 남은 필드는 재생 수명과 Unity 연결 값이고, 남은 분기 4곳은 이벤트 준비, 구간 전환, `SeekSegment`의 Sequence 전용 동작입니다. 더 나눠도 필드를 공유할 뿐입니다.
