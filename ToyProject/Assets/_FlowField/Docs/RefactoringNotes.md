# FlowField 설계 결정 기록

구조 개선에서 내린 주요 결정과 이유입니다. 단계별 상세 기록은 Git의 `c569a6c`에 있는 이 파일을 봅니다.

## 구조

| 결정 | 이유 |
| --- | --- |
| 사용자 코드를 작업 밖으로 분리 (`FlowFieldExecutionBoundary`) | 복잡성의 근원이 빌드 도중 수명을 바꾸는 콜백이었습니다. 이벤트를 작업 뒤에 전달하고 Modifier 안의 수명 명령을 거부해, 외부 호출 뒤 소유권 재검사를 115줄에서 없앴습니다 |
| Manager가 제출한 요청만 빌드 | Scheduler가 이전 요청으로 빌드하면 잘못된 설정이 그대로 풀렸습니다 |
| Volume 책임을 Tracker, Registry, SafetyState, BuildContext로 분리 | 2,812줄 Session을 책임별로 나눴습니다. 가장 큰 세션 파일은 이제 572줄입니다 |
| Surface는 빌드 단계만 클래스로 분리 | partial 파일은 필드를 공유해 읽기만 쉬워질 뿐 결합이 줄지 않습니다 |
| 호환 코드를 두지 않음 | 구버전 API 래퍼, 직렬화 별칭, 마이그레이션 코드가 없습니다. 베이크 `_formatVersion` 검사는 다른 형식을 거부하는 검증이라 유지합니다 |

## 계산과 성능

| 결정 | 이유 |
| --- | --- |
| 내비게이션을 Burst Job으로 전환하고 워커 스레드에서 실행 | 메인 스레드 2ms 예산을 쓰지 않아 프레임을 막지 않습니다 |
| GPU 경로 제거 | Player의 Goal 변경이 Surface 17~23ms 대 274~314ms, Volume 0.65초 대 3.9초로 Burst가 빨랐습니다. **이 Mac 하나의 측정 결과입니다** |
| Physics 조회는 프레임에 나누지 않음 | 표면과 장애물은 한 스냅샷이어야 합니다. Surface 첫 빌드 115~120ms는 이 결정의 비용입니다 |
| 끝난 풀이를 게시 | 움직이는 Goal에서 결과를 계속 거부해 게시가 멈췄습니다. 이전 Goal의 풀이가 잠깐 보이더라도 필드가 멈추는 것보다 낫습니다 |
| 게시 배열 재사용 | 움직이는 Volume Goal에서 GC 프레임이 28ms였습니다. 10초 GC가 330회에서 0회로 줄고, 대신 빌드 하나 분량의 메모리를 더 잡습니다 |
| Topology를 평탄 인덱스 오프셋으로 계산 | Volume 100³ 빌드의 70%였던 17.8초가 1.5초로 줄었습니다 |
| 메인 스레드 2ms를 조금 넘는 구간 유지 | Volume 최대 5.1ms, Surface Goal 변경 최대 3.7ms입니다. 프레임이 17ms 안팎이라 더 나누지 않았습니다 |

## 베이크

v6은 마이그레이션 없이 전환해 다시 Bake했습니다. 내용 해시가 v5와 같음을 확인했고, Volume Asset은 453,863바이트에서 106,568바이트로, Surface Asset은 1,286,861바이트에서 981,158바이트로 줄었습니다.

## 하지 않은 것

- **샘플 직렬화 필드의 기반 클래스 이동 취소:** 기반 클래스는 Agent 수명만 소유하고, 필드의 타입과 기본값이 샘플마다 다릅니다.
- **CI 러너 미도입:** 공개 저장소라 외부 fork가 워크플로를 수정할 수 있어, 저장소의 pre-push 훅으로 검사합니다. 훅을 켜지 않은 PC와 `--no-verify`는 막지 못합니다.
